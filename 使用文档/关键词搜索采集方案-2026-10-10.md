# 关键词搜索采集方案（抖音搜索页 → 视频/图文链接 → 评论采集）

版本：v1 草案（2026-10-10）
结论：**可行，且与现有采集引擎同源**——搜索页结果也是页面自己发的带签名接口，用现有"被动拦截响应"机制即可零破解获取，不需要任何新协议能力。

---

## 一、为什么可行（技术依据）

抖音网页版搜索页 `https://www.douyin.com/search/{关键词}?type=video`（或 type=note 图文）：

- 页面滚动加载结果时，会请求接口：`/aweme/v1/web/general/search/single/`
- 响应 JSON 内含每个作品：`aweme_id`、`desc`（标题）、`author`（昵称/uid/sec_uid）、`statistics`（点赞/评论数）、`aweme_type`（0=视频/68=图文）
- 该请求由页面自己签名，我们**钩住 response 只读数据**（与评论采集完全同机制，见 lib/ 现有实现），不构造请求、不破解签名
- 分页：响应带 `cursor` 与 `has_more`，页面自动滚就会自动翻页——驱动浏览器自然滚动即可持续拦截

**风险对比**：搜索页风控比评论页更敏感（搜索是典型机器行为场景），必须慢节奏：每次搜索间隔 ≥60s、单关键词翻页 ≤20 页、单日搜索 ≤30 个关键词、翻页间隔 4~6 秒随机。配合现有节奏系统即可。

## 二、方案设计（复用现有管线）

### 流程

```
输入关键词（可多行批量）
  → 浏览器打开搜索页（type=video 或 note）
  → 自然滚动 + 拦截 search/single 响应
  → 解析出 [{awemeId, desc, commentCount, author, workType}]
  → 按规则筛选（评论数阈值/关键词相关度/作者黑名单/已采过跳过）
  → 转成标准链接 https://www.douyin.com/video/{awemeId}
  → 直接写入现有「作品链接队列」（自动去重、冷却、强制重采全部复用）
  → 由现有采集任务逐条评论采集
```

### 采集页新增区块（不动现有结构）

```
【关键词找作品】（可折叠 panel）
  关键词输入框（一行一个，支持多个）
  [搜索范围] 视频 / 图文 / 综合
  [过滤] 最少评论数 ≥ [50] ｜ 跳过已采集作品
  [限额] 单日搜索次数上限 30 ｜ 单关键词最多 20 页
  [按钮] 开始搜索 → 结果实时显示（标题+评论数+作者，勾选后一键加入采集队列）
```

### 后端改动（最小）

| 模块 | 改动 |
|---|---|
| 新文件 `engine-search-tasks.js` | 搜索任务：打开搜索页 → 拦截 `/general/search/single/` → 滚动翻页 → 解析结果 → 落库 `search-results.json`（只存 awemeId/desc/author/commentCount/time，不存响应原文） |
| `server.js` | 新增 `/api/search/results`（读取结果、勾选转队列）、`POST /api/search/run`（启停任务）、限额字段接入每日用量 |
| `lib/` | 新增 `search-parse.js`（search/single 响应 → 标准作品条目，字段映射与现有字段文档同风格）；`page` 健康检查复用现有 `readPageHealth` |
| 采集页 | 链接队列的"＋加入队列"逻辑复用（`addHistToQueue` 同款去重） |

### 数据与隐私

- 搜索结果的作者/评论数仅存摘要字段；接口原始响应不落盘（与现有"响应原文不落库"原则一致）
- 搜索历史随 data 目录，冷却/限额沿用现有每日用量体系

## 三、分阶段落地

1. **第一阶段（1~2 天）**：搜索+解析+结果列表+勾选转队列（人工确认环节保留——搜索结果先人工勾选，符合你"少量精准"的思路）
2. **第二阶段（可选）**：搜索结果按规则**自动**加入采集队列（评论数/关键词过滤），配"先搜索后采集"一键串联任务
3. **不建议做**：全自动"搜索→采集→AI→触达"一条龙无人值守——搜索环节风控最敏感，保留人工确认开关是安全阀

## 四、与第 1 点（人工固定链接）的关系

两者互补不冲突：固定链接=精准对标用户；关键词搜索=扩大覆盖面。建议先用人工勾选模式跑 1~2 周，积累搜索限额数据后再决定是否开自动串联。
