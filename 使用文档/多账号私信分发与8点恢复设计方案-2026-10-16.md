# 多账号私信分发 + 8点恢复 最终设计（v2 专业评审版，2026-10-16）

> 版本说明：v2 在 v1 基础上完成专业评审，补齐状态机、信号分类、崩溃恢复、迁移、测试等全部工程细节。按本版实施即"一次到位"。

## 一、需求确认

1. 私信账户池：指定哪些账号参与私信、轮转顺序
2. 遇"私信频繁"：该号冷却排队尾，其他号继续；一轮结束后冷却到期再回头试
3. 遇"今日私信达上限"：该号当日彻底停用，明日早 8 点恢复
4. 所有号都不可用 → 整体停止并给出明确汇总
5. 账户池界面显示"今日已私信 X"，剩余按**经验上限**估算（程序自学）
6. 每日窗口按**运营日**（早 8:00 起算）

## 二、配置与数据模型

### 2.1 设置新增（settings.json，均有默认值 + validateSettings 校验）

| 键 | 默认 | 说明 |
|---|---|---|
| `dm.poolAccounts` | `[]` | 池成员：`[{accountId, template?}]`（template 可选，账号级私信话术覆盖，空则用全局 dm.template） |
| `dm.frequentCooldownSec` | `1800` | 首次频繁冷却 30 分钟 |
| `dm.dailyResetHour` | `8` | 运营日切点 |
| `dm.batchPerAccount` | `5` | 每账号每轮领取用户数 |
| `dm.accountSwitchIntervalSec` | `90` | 账号间切换间隔（±30% 抖动） |
| `dm.adaptiveCap` | `true` | 经验上限学习开关 |
| `dm.maxFrequentRetriesPerDay` | `2` | 单账号单日"频繁→重试"最多 2 轮，超过视同今日停用 |
| `dm.sameVideoPerBatch` | `2` | 每批内同一视频最多取 2 人（错峰） |

### 2.2 账号运行状态（data/dm-account-state.json）

```json
{ "账号ID": {
  "frequentUntil": null,            // 冷却截止（墙钟时间戳）
  "frequentCountToday": 0,          // 当日频繁次数（8点清零）
  "disabledUntil": null,            // 今日停用截止=明日08:00本地
  "lastStopReason": "",
  "opDay": "2026-10-16",            // 状态所属运营日
  "sentToday": 0,                   // 今日已确认成功私信数（8点清零）
  "capHistory": [{"date":"2026-10-15","sentAtCap":42}],  // 保留最近14天
  "estimatedDailyCap": 42,          // 最近≤3次 capHistory 的最小值
  "lastDaySent": {"date":"2026-10-14","sent":38}
} }
```

**运营日**：`store.opDayStr()` 按 `settings.human.timeZone`（Asia/Shanghai）计算，早 8:00 前算前一天。
**状态字段跨日自愈**：任何读取路径先按 opDay 检查——opDay 变了就清零 frequentCountToday/sentToday、解除已过期的 frequentUntil/disabledUntil（幂等）。
**时钟回拨**：disabledUntil 用"明日08:00的绝对时刻"计算，不用 now+24h，回拨安全。

### 2.3 分配锁（data/contact-allocation.json）

```json
{ "uid|businessId": { "accountId": "2", "kind": "dm", "plannedAt": "...", "consumed": false } }
```

- `consumed=false` 且属于其他账号 → 任何模式的触达名单都排除该用户（**单账号模式也检查**，防与分发并发双触）
- 该用户本次尝试有结果（成功/确认失败/待核验）时置 `consumed=true`
- 崩溃恢复：`pending_verification` 的 attempt 字段已原子预写（现有机制），分配锁未消费也无妨——两把锁互补，不会重发

### 2.4 每日额度（daily.json）

- 键改为**运营日** `opDayStr()`。一次性迁移：切换后旧自然日键不再读取（首日可能少计部分历史用量 → 方向是保守的，记录在升级说明）
- dm 计数沿用现有口径：`max(成功数, 尝试数)` 计入已用

## 三、平台信号分类（专业人员最关注的一块）

现有三层检测，必须明确归类，避免把"单用户拒收"误判为"账号频繁"：

| 层级 | 信号来源 | 归类 |
|---|---|---|
| 页面健康 | `readPageHealth` = `restricted`（操作频繁/功能受限提示） | **账号频繁** |
| 页面健康 | `readPageHealth` = `daily_limit`（今日次数已达上限提示） | **账号今日上限** |
| 页面健康 | `readPageHealth` = `verification`/`login` | 账号异常（验证码/登录失效）→ 当日跳过该号，汇总标注 |
| 发送回执 | protobuf 拒绝码 + 文案（如"消息检查未通过（检查码：2）"） | 新增映射表 `lib/dm-account-signals.js`：已知账号级限制文案 → **账号频繁**；已知接收人级文案 → 维持现有 recipient 处理（不换号） |
| 发送回执 | 其他明确业务拒绝 | 维持现有 confirmed_failure/recipient，不触发换号 |

**回退原则**：无法归类的拒绝 → 按接收人级处理（不动账号状态），宁可少换号、不误伤账号。
**升级原则**：`frequentCountToday` 每 +1，冷却时长翻倍（30→60→120 分钟，封顶 2 小时）；超过 `maxFrequentRetriesPerDay`（2）→ 视同今日停用（disabledUntil=明日8点）。

## 四、分发执行器（新模块 engine-dm-distribution.js）

### 4.1 流程

```
0. 预检：池内账号至少1个已登录；同IP警告（见§六）；生成 runId + checkpoint
1. 联系人池：AI=是/人工批准、无接触、重复规则、分配锁未占用 → 按评论时间新→旧
2. 分配（§五）→ 按账号切成名单块（每块≤batchPerAccount，块内同视频≤sameVideoPerBatch）
3. 轮转执行（循环）：
   cycle = 当前可用账号按池顺序各取一块名单执行（复用 outreachTask，冻结消息=账号级template||全局）
   账号状态处理：
     账号频繁 → frequentCountToday++，frequentUntil=now+cooldown(翻倍规则)，该块剩余用户回池，排到队尾
     今日上限 → capHistory 记录当日 sentToday，disabledUntil=明日8点，剩余回池
     验证码/登录失效 → 该号当日跳过（不设禁用，人工处理后可在界面"恢复账号"）
     正常完成 → 记录 sentToday、consumed、汇总
   cycle 结束条件：无可用账号 或 名单清空 或 全部账号停用
   安全阀：单账号单日 frequentRetries 超过上限 → 今日停用；全部账号停用 → 整体停止并提示
4. 汇总：每账号 成功/待核验/失败/跳过 + 待分配数（明日8点后继续）+ 各账号经验上限更新
```

### 4.2 崩溃恢复

- 分发运行中写 `task-checkpoint.json`（runId、队列快照 uid 列表、轮转游标、各账号已领块）——沿用现有 checkpoint 机制
- 启动时 state=running → 标 interrupted（现有逻辑）；**不自动续跑**，用户重新发起分发即可安全重算（分配锁 + attempt 字段保证不重复触达）

### 4.3 与现有引擎的关系

- 完全复用 `outreachTask`（每账号×一块=一次任务），关注/私信核验、protobuf 回执、节奏、健康检查全部沿用
- 唯一改动：`engine-actions.runTask` 的身份校验从"采集账号一致"改为"分配方案允许"；`saveContactObservation` 允许跨账号（观察记录自带 accountId）

## 五、分配算法（每用户选账号）

1. **经验剩余**（estimatedDailyCap − sentToday，与设置额度取小）最大
2. 当日已用最少
3. 登录健康（未登录/验证码号跳过）
4. 该视频已分配给该号人数最少（错峰）
5. 全无 → "待分配"队列（界面显示数量，明日8点优先）

**经验上限学习**：平台报"今日上限"时记录 `{opDay, sentAtCap}`；`estimatedDailyCap` = 最近14天内 ≤3 次样本的最小值；无样本 → 用 `lastDaySent` 作参考值并标注"参考"。估算只影响分配与显示，不硬拦；每自然日每号只记一次样本（首个信号优先）。估算偏离时由状态机兜底并自动修正样本。

## 六、一账号一 IP 预检（新增）

分发开始前：池内账号两两比较代理 host（无代理视为同一 IP 组）→ 同 IP 的账号给出醒目警告并要求确认后才继续；全部无代理 → 同样警告。**不强制阻止**（测试环境），但默认高亮风险。

## 九、测试计划（实施时同步完成）

1. **状态机**（假时钟）：频繁→冷却翻倍→队尾→到期回队；超 2 次→今日停用；8点跨日自愈；时钟回拨不提前解禁
2. **信号分类**：用真实文案样本（含"检查码：2"类回执、页面频繁/上限文案）验证归类表；未知文案回退接收人级
3. **分配**：经验剩余优先、同视频错峰、锁防双发、待分配队列
4. **恢复**：checkpoint interrupted 后重跑不重复触达（pending 块 + 锁）
5. **迁移**：旧 daily 键→运营日，首日保守少计
6. **回归**：现有 720+ 单元测试全绿 + 构建流水线全绿

## 十、边界与风险（最终版）

1. 平台文案变化 → 未知信号按接收人级回退，不误伤账号，只损失一次自动换号机会
2. 8 点窗口是程序内部口径；平台若 0 点重置，0~8 点实际可发但程序 8 点才放行——保守方向
3. 一账号一 IP 为红线（预检警告）；同 IP 多号=集中暴露
4. 经验上限永远只是参考；状态机兜底 + 样本自动修正
5. 多号共用同一套话术模板仍是风险点 → 池支持账号级话术覆盖（§2.1），后续接 AI 个性化话术更佳
6. 单账号模式与分发模式互斥：任务运行中禁止切换模式（复用现有"任务运行中不可改设置"约束）
