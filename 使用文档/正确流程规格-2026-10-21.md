# 华贸获客 · 正确流程规格（基于真实账号实测）

- 版本：v1（2026-10-21）
- 依据：2026-10-20/21 用测试号在真实抖音页面上实测（流水账见 `D:\dy-live\core-run*\trace.jsonl`）
- 适用代码：`dy-lead-app/core/`（按本规格从头重建的核心流程）
- 原则：**页面元素只负责“做动作”（打开、输入、点击、滚动）；结果、状态、身份一律以平台自己的接口响应为准**。不构造、不重放任何签名请求。

每一步都按同一格式写：**动作 → 应收到的响应 → 成功判定 → 异常与处理**。标注「实测」的是在真实页面上看到的事实，标注「待测」的是还没有实网样本、需要下一轮确认的部分。

## 0. 账号会话

| 项 | 规格 |
|---|---|
| 浏览器 | 系统 Chrome / Edge，每个账号一个持久化资料目录；登录一次长期有效 |
| 登录判定 | 以最近一次 `GET /aweme/v1/web/user/profile/self/` 成功响应为准：`status_code=0` 且 `user.sec_uid` 存在 → 已登录（实测：打开首页后 0.5–36 秒内出现；之后浏览各页面也会周期性出现） |
| 未登录 | 首页 30 秒内没有成功的 profile/self → 提示人工扫码，最多等 15 分钟 |
| 不要做的事 | **不要在每次跳转后用页面 DOM 重新判定登录**。实测：旧流程在新搜索页 `/jingxuan/search/…` 读不到登录标记，判为“尚未取得可靠登录证据”并停止任务，而同一时刻 profile/self 刚确认已登录 |
| 安全验证 | 页面出现验证码弹层（`[id*=captcha]`、`[class*=captcha]`、`[data-e2e=verify-popup]` 或“请完成验证/拖动滑块完成验证”）→ 进入“等待人工验证”，**窗口保持打开**，人工完成后自动继续；连续 3 次检查（约 9 秒）不再出现弹层才算完成。不自动处理、不绕过 |
| 实测 | 程序的浏览器在第一次搜索时就出现滑块验证（两次运行都出现）；人工完成后同一会话后续搜索与采集都正常。旧流程遇到验证直接结束并关闭窗口，用户来不及完成——必须改为“等待人工” |

## 1. 关键词搜索

| 项 | 规格 |
|---|---|
| 动作 | 打开 `https://www.douyin.com/search/<关键词>`（综合）；视频/图文范围加 `?type=video` / `?type=note`。也可从首页搜索框输入后回车，实测会落到 `/jingxuan/search/<关键词>` |
| 第 1 页响应（实测） | `GET /aweme/v1/web/general/search/stream/?keyword=…&offset=0&count=10`，**分块流式**，正文可能是多段 JSON；用文本读取后按顶层 JSON 对象切段解析（`lib/search-works.js` `parseSearchBody`） |
| 第 2 页起（实测） | `GET /aweme/v1/web/general/search/single/?offset=10&count=10`（第 3 页 offset=20…）。页面空闲时常会自动预取；否则滚动结果列表触发，实测滚动后约 1 秒到达 |
| 每条结果字段 | `data[].aweme_info`：`aweme_id`、`desc`、`aweme_type`（68=图文）、`statistics.comment_count`、`author.sec_uid/nickname`；分页 `has_more`、`cursor` |
| 成功判定 | 第 1 页收到 **作品数>0** 的响应；翻到第 N 页 = 收到 `offset=(N-1)*10` 的响应，或 `has_more=0` 提前结束 |
| 空首页（实测） | 第一页可能先返回 `status_code=0` 但 **0 条作品**的空结果，约 30 秒后页面自动重取到真结果。**空响应不等于没有结果**：第一页等到“有作品”为止（上限 40 秒），仍为空则隔 20–30 秒重开一次，两次都空才判“无结果/被限流” |
| 验证 | 第一页为空且页面出现验证弹层 → 等人工验证 → 重开搜索页 |
| 结果卡片 | 实测：结果卡片不是 `<a href>` 链接，点击是浮层播放并自动连播。**作品 ID 只从接口响应取**，不要从 DOM 抓链接或点卡片 |
| 节奏 | 关键词之间 30–60 秒；翻页之间 1.5–3 秒 |

## 2. 作品评论采集（视频 / 图文同一流程）

| 项 | 规格 |
|---|---|
| 动作 a | 打开 `https://www.douyin.com/<video|note>/<aweme_id>`（类型取自搜索结果的 `aweme_type`） |
| 动作 b：读内嵌第一页 | 读页面 `self.__pace_f` 中的 `comment:{statusCode, hasMore, total, cursor, comments:[{cid, text, createTime, user:{uid, secUid, nickname}}]}`（驼峰字段，`lib/page-comments.js`） |
| 实测：图文 | 直接打开图文时**第一页评论只在内嵌数据里**，点“评论”页签后页面**不会**请求 `comment/list`。评论不满一页（如 12 条）的作品永远不会出现评论接口响应——旧流程因此暂停，即“页面已显示到底，程序却认为没完” |
| 实测：视频 | 视频页**没有**内嵌评论；评论区默认展开，打开即请求 `comment/list?cursor=0`（首页只有 5 条），之后每页 10 条 |
| 动作 c：翻页 | 内嵌 `hasMore=1` 或无内嵌数据时：图文先点“评论”页签（默认停在“相关推荐”，页签是普通 `div`，文字形如 `评论(12)`）；然后把**评论列表容器**滚到底 |
| 翻页响应（实测） | `GET /aweme/v1/web/comment/list/?aweme_id=<id>&cursor=<n>&count=10`：`status_code=0`、`comments[]`、`has_more`、`cursor`、`total`；每次滚到底约 2–5 秒到下一页 |
| 字段 | `comments[].cid`（去重键）、`text`、`create_time`（秒）、`ip_label`、`digg_count`、`reply_comment_total`、`label_type`（1=作者）、`user.uid/sec_uid/nickname` |
| 内嵌数据时机（实测） | 内嵌评论随页面**流式到达**：打开后 2.8 秒读取为空，稍后才出现。读不到时每秒重读，最多 6 次；视频页本来就没有内嵌评论，不必等 |
| 第一页漏采（实测） | 某图文第一次运行没读到内嵌数据，页面随后自己请求了 `cursor=20` 的第二页（6 条，`has_more=0`），程序据此判“完整”，实际漏了前 20 条（第二次运行正确得到 26 条）。**规则：主列表最早收到的是 `cursor>0` 的页、又没有内嵌第一页 → 第一页缺失，先补读，补不到就记 `partial`，不能判完整** |
| 图文评论页签（实测） | 右侧栏 `相关推荐 / 评论(173)`，评论页签是无 role 的普通 `div`（类名随机），**页面加载几秒后才渲染**：打开后 2 秒找不到，6 秒能找到。必须等待重试（最多 10 秒），不能只试一次。未点开时评论列表 `data-e2e="comment-list"` 挂在 DOM 里但不可见，里面甚至已有“暂时没有更多评论”文字——**结束文字只认可见列表里的** |
| 两条评论列表（实测） | 后台预取：`comment/list` 不带 `insert_ids`，图文未打开评论时也会自动请求 cursor=20、40…，其 `has_more` 不稳定（同一作品一次报 0、一次报 1）。可见列表：点开评论页签后请求的 `comment/list` **带 `insert_ids`**，从 cursor=0 起每页 10 条，随滚动推进。两条都收、按 cid 去重；**完成只看滚动所推动的那条（可见列表）**。173 条评论的图文按此规则采到 53 条一级评论并完整结束；按旧规则（以不带 insert_ids 的列表为准）会在 23 或 37 条处误判 |
| 登录必要性（实测） | 未登录的浏览器也能看到评论，但滚动翻页会停滞（同一图文只采到 36 条后连续无进展），采集必须在已登录状态下进行 |
| 完成判定（任一） | ① 滚动所推动的可见列表返回 `has_more=0`；② 出现过的所有列表都返回过 `has_more=0`（含内嵌第一页 `hasMore=false` 且没有其他列表）；③ **可见**评论列表里出现“暂时没有更多评论”且本轮滚动没有新响应 |
| 未完成 | 连续 3 轮无新评论且无结束标记 → `interrupted`；达到轮数上限 → `partial`；都要记原因 |
| 范围 | 只收一级评论（二级回复是业务取舍，暂不采） |
| 节奏 | 作品之间 8–15 秒；翻页之间 1.8–3.5 秒 |
| 单作品失败 | 只影响本作品（记原因，继续下一个）；只有验证未完成、登录失效这类账号级事件才停止整个任务 |
| 每个作品的登录复核（软件） | 作品页打开（含人工验证）之后、读评论之前，用与预检查相同的登录检查复核一次：已退出 / 需验证 / 证据不足 → 本作品记 `interrupted`，原因与任务提示、账号卡片同一句，整个队列暂停。页面明确“仍在加载”（SPA 正文未就绪）最多等 40 × 0.5 秒；页面切换中最多重查 3 次。实现：`core/collect.js` 的 `afterOpen` 钩子 + `engine-core-collect.js` |
| 作品资料（软件） | 采集时同时收页面自己请求的 `/aweme/v1/web/aweme/detail/`（只认目标 `aweme_id`）与作品页内嵌数据，写入作品描述 / 标题 / 作者 / 统计 / 来源路径（AI 判断与“视频描述”列使用）；作者本人的评论标为作者。与旧采集共用 `lib/work-record.js` |

## 3. 筛选与需求判断

实测数据（2026-10-21，两个关键词各 2 页 → 33 个作品去重后约 30 个 → 一级评论约 700 条）：

| 环节 | 数量 | 说明 |
|---|---|---|
| 最近 3 天、非作者的一级评论 | 51 | 按 `create_time`（秒）计算，全部评论都带时间 |
| 其中同行服务商 / 收店铺 / 物流广告 | 约 25 | 昵称带“申诉”“跨境”“店铺转让/收店铺”，或评论是“可以处理”“能接”“发您题库”“p4二审已突破”等揽客话术 |
| 空文本 / 纯表情 / 无关 | 约 13 | |
| **明确需要帮助（A 类）** | **9** | 问价格、认证/视频验证失败、问怎么联系、问如何激活、申诉多年未解决、回复“需要” |
| 需求较弱（B 类） | 4 | 要申诉模版（想自己处理）、物流商替客户询问 |

判断规则：
1. **先排除同行**：昵称或评论含服务商特征（申诉/跨境服务/店铺转让/收店铺/海外仓/物流 + 揽客话术）一律排除；同一作品下作者自己的回复（`label_type=1`）排除。
2. **再判需求**：评论描述了自己的账户问题（停用、视频认证失败、协议三、扫号、冻结、激活），或在服务类作品下主动询问价格/联系方式/“需要” → A 类。
3. 只要模版、只问“什么原因”“成功了吗”的围观提问 → 不联系或 B 类人工决定。
4. 同一用户多条评论只联系一次（按 `sec_uid` 去重）。

## 4. 关注与私信

实测（2026-10-21，A 类 9 人，测试号，单账号顺序执行，用户间隔 25–40 秒，满 5 条私信休息 90–180 秒）：

### 4.1 打开主页

| 项 | 规格 |
|---|---|
| 动作 | 打开 `https://www.douyin.com/user/<sec_uid>` |
| 应收到的响应 | `GET /aweme/v1/web/user/profile/other/`：`user.sec_uid`、`user.follow_status`（0 未关注 / 1 已关注 / 2 互关 / **4 已请求**——对方为私密账号，关注需对方同意）、`follower_status` |
| 实测 | 9 次中 8 次 4–6 秒内到达；1 次 10 秒内未到，重开后正常 → 未到时重开一次再跳过 |

### 4.2 关注

| 项 | 规格 |
|---|---|
| 判断是否需要 | 以主页响应 `follow_status` 为准：1/2 → 已关注不点；4 → 已请求不点；0 → 点 |
| 动作 | 点击前**现找**按钮：`[data-e2e="user-info-follow-btn"]`，可见、文字恰为“关注/回关”的唯一一个；只点一次 |
| 应收到的响应（实测） | `POST /aweme/v1/web/commit/follow/user/`，表单 `type=1`、`user_id=<数字UID>`；响应字段 `status_code、status_msg、follow_status、is_enterprise、footer、is_biz_account、extra、log_pb`（**不含用户 ID**）；`follow_status=1` 成功，**4 = 私密账号已发出请求**（不是失败）。点击后约 2 秒到达 |
| 成功判定 | 只认点击后 10 秒内本页、`type=1` 且 `user_id`=目标数字 UID 的请求的响应 `status_code=0` 且 `follow_status∈{1,2}`；4 记“已请求”；无响应记“待核验，禁止自动重试” |
| 旧实现问题（实测） | 先把按钮记成长串 `nth-child` 路径，500 毫秒内重定位时主页已重绘 → 9 人中 4 人“定位出错/没点上”；点中的 5 人平台都返回 `status_code=0, follow_status=1`，却因回执匹配规则对不上全部记成“待核验”。新实现 6 次点击 6 次确认 |

### 4.3 私信

| 项 | 规格 |
|---|---|
| 动作 | 主页资料区“私信”按钮 → 等聊天层 → 核对接收人 → 读聊天历史（已发过则跳过）→ 填写 → 发送按钮点一次 |
| 应收到的响应（实测） | `imapi.douyin.com` 二进制协议：发送请求 `cmd=100`，回执 `status=0` 且带服务端消息 ID，与本次请求、发送者、客户端消息 ID 匹配 → 确认送达 |
| 实测结果 | 8 人尝试：**7 人确认送达**（全部有协议回执，发送后 1–3 秒确认）；1 人跳过（聊天中已有本账号发出的消息，需人工确认是否此前手动联系过）；1 人（私密账号，关注为“已请求”）点私信后 16 秒内聊天层未出现（无输入框、无消息列表）→ 记“未发送”，不重试 |
| 接收人核对 | 本轮均以主页昵称与聊天标题一致确认（`dom_profile_name`）；协议会话标识核验需继续积累样本 |
| 频繁 / 上限（第二批实测） | 同一测试号当天：上午 7 条（16:59–17:10）→ 下午第二批 11 条（18:18–18:26，用户间隔 15–25 秒）全部送达；**第 19 次起被拒**。拒绝回执：协议 `cmd=100`、`status=0`、**`send=3`、`check_code=2`**，按 `lib/dm-rejection.js` 归类为“私信操作频繁”（账号级）。关注同期 18 次（16 成功、2 次私密账号 `follow_status=4`）**未触发限制**。结论：本账号陌生人私信约在“当天第 18 条、或 8 分钟内连发 11 条”后进入频繁；冷却时长待测 |
| 频繁后的处理 | 回执 `failureScope=account` → **立即停止整个任务**，记录停在第几位、当天已发几条、拒绝回执原文；不对后续用户继续尝试（实测旧版漏判，又被拒 4 次）。多账号时该账号进冷却、排到队尾，其余用户回池给其他账号 |
| 频繁 / 上限（首批） | **首批 7 条私信 + 6 次关注未触发任何“操作频繁”或“今日上限”提示**。出现时按 `lib/dm-rejection.js` 的精确文案归类：账号级（频繁 / 今日上限）→ 立即停止整个任务并记录停在第几位；接收人级（仅互关可发 / 对方消息上限）→ 只记本人失败 |
| “点了没反应” | 实测复现 1 例，对象为私密账号。规格：点击私信后 16 秒内没有聊天层 → 记“未发送 + 原因”，继续下一位，不影响其他用户 |

### 4.4 每个用户的结果状态

`confirmed_success`（有平台回执）/ `confirmed_failure`（平台明确拒绝，带原文）/ `pending_verification`（动作已做但没拿到回执，禁止自动重做）/ `already`（已关注）/ `skipped`（已私信过等）/ `not_sent`（没做动作，带阶段与原因）。重跑时有确定结果的用户自动跳过，不会重复发送。


## 5. 频繁、冷却与限额（2026-10-21 晚实测，测试号单账号）

| 时间 | 事件 |
|---|---|
| 16:59–17:10 | 第一批 7 条送达 |
| 18:18–18:26 | 11 条送达（用户间隔 15–25 秒），第 12 次起被拒：回执 `send=3`、`check_code=2`（带“操作频繁”文本，business=7180） |
| 18:45 / 18:55 / 18:58 | 每 10 分钟试发 1 条，均被拒 |
| 18:58 → 19:59 | **完全安静 61 分钟** |
| 19:59–20:09 | 第一条即恢复，**再送达 12 条**，第 13 次被拒 |
| 20:09 → 21:09 | **完全安静 60 分钟** |
| 21:09 | 恢复，送达 1 条；随后 9 人收到 `send=3/check_code=2` 但**没有提示文本**，第 10 人才带“操作频繁”文本 |
| 21:16 → 次日 00:48 | **完全安静约 3.5 小时**后试发 1 条（老会话，聊天正常打开）仍是 `send=3/check_code=2` → 不是 60 分钟冷却，是**当日额度**；停止，次日再发 |

| 次日 第二个号（崔广安，公司业务号） | 每 10 人休息 60 分钟：首轮 10 人送达 8；改为“每 5 人休息 5 分钟”后：16 分钟内连续送达 10 条，第 11 条频繁；**按规则暂停 30 分钟后试发即恢复**，之后又送达 8 条无频繁。该号当日累计送达 26 条 |
| 同上 | 3 人被跳过：聊天里有该号**前天**发出的另一条揽客消息（公司人工发过），平台提示“对方回复或关注前只能发一条”，跳过正确 |

结论与规则：
1. **每次连续发送约 11–12 条即触发频繁**；当天累计约 32 条后恢复窗口缩到 1 条，之后安静 3.5 小时仍被拒——**新号陌生人私信当日额度约 30 条**，到量即停到次日（实际额度随账号权重变化，以回执为准）。
2. **触发后保持完全安静 60 分钟再试 1 条**；30 分钟内反复试探全部被拒（试探本身可能延长冷却）。**软件节奏（用户确认，2026-10-21）**：单号每发 5 人休息 5 分钟；多号每号发 5 人立即切换下一个号，所有号都发过一轮后统一休息 5 分钟；某号频繁 → 从触发时刻起暂停 30 分钟、仍频繁 1 小时、再仍频繁 2 小时，连续试发 3 次仍频繁按今日上限停用（期间发出过私信则阶梯重新从 30 分钟算）；显示今日上限 → 当天停用。均可在设置中调整；“5 人 / 5 分钟”节奏尚待实测是否更早触发频繁。
3. **`send=3` 且 `check_code=2`：一律按账号级“操作频繁”处理并立即停止**，不论有没有提示文本（实测无文本的 9 次也是限流）。有“请勿重复发送”“仅互关可发”等可识别文本时按文本归类。
4. 平台规则（会话列表原文）：“对方回复或关注你之前，只能发送一条文字消息。”——对同一陌生人只能发 1 条，重复联系须等对方回复/关注。
5. **限流期间点的关注会被静默撤销**：多人关注回执成功（follow_status=1），1 小时后主页显示未关注。限流时不要关注；已关注过的人不再重复点关注。

## 6. 私信“点了没反应”（只出会话列表）

实测：点“私信”后页面调用 `POST /v2/conversation/create`（cmd=609）**返回成功（status=0、OK，带会话 ID）**，但私信抽屉只显示会话列表，不打开聊天，目标也不在列表里。
- 只发生在**首次联系（新建会话）**的用户；已有会话的用户（发过消息的）即使账号限流也能正常打开聊天。
- 与对方主页隐私字段无关（`message_chat_entry=true`、`secret=0` 的用户同样出现）。
- 第二次点“私信”会被已打开的抽屉挡住（诊断 `DM_ENTRY_CLICK_BLOCKED`）。
- 复测（次日 00:4x）：同样操作下，当时“只出列表 / 聊天未就绪”的叶惠美、宇众不同**第一次点私信就正常打开聊天**（会话在当时已建好，再打开与老会话一样）。
- 处理规则（已实现，`core/outreach.js`）：出现 `DM_MESSAGE_LIST_ONLY` / `DM_TARGET_CHAT_NOT_READY` → Esc 关抽屉、等 3–5 秒、重新加载主页、再点一次私信（只重试一次，不涉及发送）；仍不行记“未发送（打开会话失败）”继续下一位，**过后（下一批）再试一次**，累计 2 次打不开才算定论（`core/run-outreach.js`）。不计账号异常。
