## 1. 一轮完整操作的时间线

`runTask(accountId, kind, options)`（`engine-actions.js:524`）→ `makeScheduler(settings, { errorBoundary: 'user' })` → `launchAccount(accountId, { headless: false })` → 逐用户循环：`visit → (doFollow ? followOne) → (doDm ? dmOne)`。`kind ∈ follow|dm|outreach`，outreach 计划内每位用户同时冻结 follow+dm。计划经 `resolvePlan` 校验：`planId` 存在、`accountId/kind` 匹配、`schemaVersion === 3`、未 `consumed`、`expiresAt`（创建后 30 分钟）未过期、`contactPolicy` 与 `settingsFingerprint` 均与当前设置一致；任务开始即 `plan.consumed = true`。运行中每次 `currentSettings(plan)` 再验指纹，不一致抛 `TaskStopError('PLAN_CHANGED')`。

| 阶段 | 执行动作 | 监听请求/响应（路径·关键字段） | 判定条件与分支 |
|---|---|---|---|

## 2. 关注状态机

### 2.1 主页关系观察 `observeProfileRelation`（`lib/profile-relation-observer.js`）

- **监听接口**：GET `https://www.douyin.com|douyin.com/aweme/v1/web/user/profile/other/`（可带结尾 `/`），仅主 frame。
- **请求条件**：查询参数 `sec_user_id` 恰好一个且等于 `targetSecUid`（即 `lead.uid`）；`uid`、`user_id` 各至多一个且互相一致、与 `targetNumericUid`（`lead.UID`）一致。
- **响应条件**：status 200、`content-type: application/json`、体 ≤ 512KB、`status_code === 0`、`user.sec_uid === sec`、`[user.uid, user.uid_str, user.user_id]` 归一化后一致、`user.follow_status ∈ [0,1,2]`。
- **state 枚举**：`not_following`（follow_status=0）｜`following`（=1/2）｜`unknown`（无响应/窗口关闭/超时）。源码注释官方 PC IM 映射：`Unknown=-1, UnFollow=0, Followed=1, FollowEach=2, Requested=4`；`follow_status=4` 不在接受范围 → 保持 `unknown`。
- 参数：`MAX_WINDOW_MS=30000`、`MAX_REQUESTS=24`；结果字段 `{state, source:'browser_profile_response', evidence:'profile_follow_status_'+值}`；只接受序号最新的响应（`latestAccepted`）。
- `visit()` 中 `relation.wait({timeoutMs: deps.historyTimeoutMs ?? 1500})`；`relation.state === 'following'` 时 `followOne` 直接跳过（`skipAction` 文案「本次主页响应确认当前账号已关注，继续处理私信」）。观察值经 `saveObservation` 落库为 `followObserved`。

### 2.2 `prepareFollow` 返回的 `prepared.state` 全部取值（`lib/outreach-browser.js`）

- **`'ready'`**：`inspectControls(kind:'follow')` 在 `profileControls()`（排除普通导航/推荐/评论/消息区、外国用户卡片、recipient 不匹配节点）中找到唯一一个标签匹配 `/^(?:[+＋]\s*)?(?:关注|回关)$/` 的控件 → 返回 `{state:'ready', click()}`。
- **`'already'`**：唯一控件标签匹配 `/^(?:已关注|关注中|互相关注)$/` → `prepareFollow` 返回 `{state:'already', reason:'目标主页显示已关注，本次没有点击'}`。`followOne` 对其执行 `saveObservation(follow, {state:'following', source:'profile_control', evidence:'目标主页控件明确显示已关注或互相关注'})` 后跳过。
- **`'missing'`**（`inspectControls` 内部枚举 `missing`）：无匹配控件 → `prepareFollow` 包装为 `{state:'missing', reason:'目标主页未找到可操作的关注控件，本次没有点击'}`。
- **`'ambiguous'`**（内部枚举）：候选>1、already>1 或二者并存 → `{state:'ambiguous', reason:'目标主页有多个关注控件，无法唯一定位，本次没有点击'}`。
- `followOne` 中 `prepared.state !== 'ready'` → `saveFollowResult({state:'confirmed_failure', reason: prepared.reason || '没有找到唯一可用的目标关注控件，本次未点击', evidence:'未执行关注点击'})`，返回 `{state:'confirmed_failure', anomaly:true}`（不点、不占额度）。
- `click()` 内部（单次使用，二次调用抛 `FOLLOW_PREPARATION_CONSUMED`）：`beforeUiAction`（→ `scheduler.before({kind:'ui'})` 授权）→ 至多 3 次重新解析（React 替换）→ 以 Playwright 原生 `handle.click({timeout:2000})` 点击 → `true`。

### 2.3 点击后回执核验 `createFollowReceiptObserver`（`lib/action-receipts.js`）

- **监听**：POST `https://www.douyin.com|douyin.com/aweme/v1/web/commit/follow/user/`（`FOLLOW_PATH`，精确等于），仅主 frame；表单参数（URL query + `application/x-www-form-urlencoded` body）每个键唯一。
- **目标匹配**：`sec_user_id` 或 `user_id` 必须命中目标且无冲突；该路径还要求 `type === '1'`（`requireFollowType`）。
- **成功判定**：响应 status 200 → 体 ≤ 64KB → JSON → `payload.status_code === 0` 且 `payload.follow_status ∈ [1,2]`；若 `payload.sec_user_id` 存在必须等于目标 sec uid；若 `payload.user_id` 存在必须为安全整数且等于目标 numeric uid → `finish({state:'confirmed_success', reason:'', evidence:'本次同页目标关注 POST 返回 status_code=0 且 follow_status=1/2'})`。
- **超时/中断**（一律 pending，禁止自动重试）：默认 `timeoutMs = 5000`（`createFollowReceiptObserver` 默认值；`deps.receiptTimeoutMs` 未传时即 5000），夹取 `[1,15000]` → `pending('未取得本次目标明确关注回执，需人工核验，禁止自动重试')`；页面关闭 → `pending('账号窗口已关闭，本次关注待核验，禁止自动重试')`；abort → `pending('任务已停止，本次关注待核验，禁止自动重试')`；`dispose()` → `pending('本次关注没有明确网络回执，需人工核验，禁止自动重试')`。`pending()` = `{state:'pending_verification', reason, evidence:''}`。

### 2.4 FOLLOW_* 错误码清单（全部由适配器 click() 抛、带 `actionNotStarted:true`）

| 错误码 | 含义（源码文案） | 处理 |
|---|---|---|
| `FOLLOW_ALREADY` | 点击前重新解析发现目标主页已显示关注关系 | 可恢复：回滚本次准备快照（`previousFollow`）后 `skipAction('主页已显示关注关系，本次未点击，保留原有关注记录')` |
| `FOLLOW_CONTROL_AMBIGUOUS` | 目标主页出现多个关注控件 | 可恢复：保存 `confirmed_failure`（reason=`[FOLLOW_CONTROL_AMBIGUOUS] …`）→ 重新健康检查 → `{state:'confirmed_failure', anomaly:true, skipped:true}`（skipped 不计物理动作，但失败态照常显示） |
| `FOLLOW_CONTROL_UNAVAILABLE` | 目标主页关注控件已不可用 | 同上 |
| `FOLLOW_CONTROL_CHANGED` | 准备后的目标关注控件持续改变（3 次重解析未稳定） | 同上 |
| `FOLLOW_PREPARATION_CONSUMED` | 本次关注准备已使用，禁止重复点击 | 不在 `RECOVERABLE_FOLLOW_CODES`，按普通异常处理 |

`RECOVERABLE_FOLLOW_CODES = ['FOLLOW_ALREADY','FOLLOW_CONTROL_AMBIGUOUS','FOLLOW_CONTROL_UNAVAILABLE','FOLLOW_CONTROL_CHANGED']`（`engine-actions.js:13`）。可恢复条件：`error === adapterClickError && !(error instanceof TaskStopError) && error.actionNotStarted === true && RECOVERABLE_FOLLOW_CODES.has(error.code)`。恢复路径会重新跑一遍「授权 + `checkPageHealth`」，因为本地控件失败不说明登录/目标身份/授权问题。

### 2.5 `pending_verification` 的产生条件（follow）

1. 点击前原子落库：`followState/followOutcome = 'pending_verification'`，`followFailedReason = '关注操作准备执行，等待状态核验'`（进程崩溃也不会自动重发）；
2. 回执等待超时 / 页面关闭 / abort / dispose（见 §2.3）；
3. catch 中 `clickStarted && !notClickedConfirmed`：点击已发生但无法证明失败 → 保存 `pending_verification`；
4. `saveFollowResult` 内的 `settledAttempt` 保护：若当前线索同 uid 且 `followAttemptId === attemptId` 且 state 为 `confirmed_success`，或 `confirmed_failure` 且（人工核验行或已有 `followEvidence`）→ 保留既有结论（`alreadySettled:true`，evidence 兜底「同次操作已有人工核验结论」）；attemptId/uid 不匹配 → `TaskStopError('ACTION_ATTEMPT_CHANGED')`。

失败证据值枚举：`'未执行关注点击'`（控件未就绪/ambiguous）、`'没有执行关注点击'`（点击异常/被中断）、`'关注适配器确认没有点击'`（click() 返回 false）、成功证据见 §2.3。

### 3.2 发送回执核验：protobuf cmd100（`lib/dm-receipt-observer.js` + `lib/dm-protocol.js`）

**监听**：POST `https://imapi.douyin.com/v1/message/send`（可带 `/`），仅主 frame，`content-type ∈ {application/x-protobuf, application/protobuf, application/octet-stream}`；窗口 `WINDOW_MS=30000`，最多 32 个请求，体 ≤ 128KB。窗口内出现两个不同 `clientMessageId` → `ambiguous` → 结果作废（outcome=null）。

**请求解析 `parseSendRequest`**（信封 schema `{1:'v',2:'v',6:'v',8:'b'}`；send 体 schema `{1:'s',2:'v',3:'v',4:'s',6:'v',8:'s',9:'reject',11:'reject',14:'v',33:'v',50:'reject',51:'reject',52:'reject'}`）：
- 信封 field1 = 命令 `100n`；field2 = `sequenceId`（正）；field6 = `inboxType`（≤ `0x7fffffff`）；
- send 体：field2 = `1n`；field6 = `7n`（文本类型）；field8 = `clientMessageId`（1–256 字符、无控制符）；field4 = 内容，经 `plainText` 解出（JSON 串 round-trip 相等，键 ∈ `{aweType,type,richTextInfos,text}` 或恰为 `{text}`，`aweType===700`、`type===0`）且必须逐字等于本次 message；
- field1 = 会话串，正则 `^0:1:(\d{1,18}):(\d{1,18})$` 且 `a < b`，一方必须等于 `targetNumericUid`（`lead.UID`），另一方记 `otherParticipantUid`；field3 = `conversationShortId`；field14 存在必须为 0；field33 存在必须等于目标 uid；
- 记录：`{sequenceId, clientMessageId, conversationId, conversationShortId, targetNumericUid, otherParticipantUid, senderVerified, inboxType, messageHash: sha256(文本)}`。

**响应解析 `parseSendResponse`**（信封 schema `{1:'v',2:'v',3:'v',5:'v',6:'b',13:'v'}`；send 体 schema `{1:'v',3:'v',4:'s',5:'v',6:'s',7:'s',8:'v',10:'b'}`）：
- 信封 field1 = `100n`、field2 = 请求 `sequenceId`（串等）、field3 必须为 `0n`（外层状态）、field5 必须 = `inboxType`；field13（发送者 uid）= `otherParticipantUid`（缺省则要求 `senderVerified`）；
- send 体 field4 = 请求 `clientMessageId`；field8（异步标志）必须缺省或 0（否则非最终结果，丢弃）；field7 存在时须经 `plainText` 解出且 sha256 等于请求 `messageHash`；field10 会话嵌套（`{1:'s',2:'v',3:'v',9:'v'}`）：field1=`conversationId`、field2=`conversationShortId`、field3=`1n`、field9=`inboxType`；
- **send 体 field3 = 服务端状态 `status`**：
  - `status === 0`：**平台已接受**。还需 field1（服务端消息编号）为正整数 → `{state:'confirmed_success', reason:'服务端已接受本次私信', evidence:'im-protobuf:cmd=100;status=0;send=0;matched-request+sender+client;server-id-present'}`；
  - `1` → `'服务端拒绝本次私信：发送者不在会话中'`；`2` → `'服务端拒绝本次私信：会话检查未通过'`；`3` → `'服务端拒绝本次私信：消息检查未通过'`（field6 拒绝文案再经 `classifyRejection` 精确匹配，命中则 `[DM_*] 理由` + `failureScope:'recipient'`；field5 为正 → 追加 `（检查码：X）`）；`4` → `'服务端未向目标正常发送本次私信：仅自己可见'`；
  - 未识别状态/任何校验失败 → 返回 null → 保持 pending。

**确认「平台已接受」的证据链**：命令 cmd=100、请求-响应 `sequenceId` 一致、发送者 uid（field13 或请求自证）、`clientMessageId` 一致、消息文本 sha256 一致、会话 id/shortId/inboxType 一致、外层 status=0、send status=0、**服务端消息编号（field1）存在**。证据串见上。

**回执观察器组合 `createDmReceiptObserver`**（`lib/action-receipts.js`）：
- strict protobuf `observeDmSendReceipt` 的 onOutcome → `events.push({path:'/v1/message/send', protocol:'im-protobuf-cmd100', targetMatched:true, state, evidence, at})` 并 settle 两个等待；
- legacy 候选：路径正则 `/^\/(?:aweme\/v1\/web\/(?:im|message|private_message)\/|im\/(?:v\d+\/)?)(?:message\/)?send\/$/`，POST 表单键 `sec_user_id/to_sec_user_id/recipient_sec_uid`、`user_id/to_user_id/recipient_uid` 目标匹配，仅推事件、**绝不释放 waitForReceipt**（源码注释：非权威）；
- 诊断：`imapi.douyin.com /v1/*` 的传输元数据（去敏路径、content-type、status、phase），窗口 5000ms，仅日志（`scope:'transport_metadata', protocolEvaluation:'not_performed'`）；
- `waitForReceipt({timeoutMs})`：已有 outcome 立即 true；否则等待 `min(protocol.remainingMs(), timeoutMs || 30000)`；超时/关闭/abort → false（不产生失败结论）；
- `getOutcome()` = `protocol.outcome() || pending('尚未取得本次目标消息的明确业务回执，需人工核验，禁止自动重发')`；
- 默认 `dmVerifier`（`engine.js:29`）即 `receipt.getOutcome()`；结果再经 `workflow.validateDmOutcome`：state 必须 ∈ DM_STATES、非 pending 必须有 evidence，reason ≤200 字、evidence ≤300 字，`failureScope:'recipient'` 透传。

### 3.3 接收人限制（recipient restriction）识别

三层：
1. **protobuf send status=3 + field6 文案** → `classifyRejection` 精确匹配 `REJECTION_RULES`（`lib/dm-rejection.js` 全文案列表）→ `failureScope:'recipient'`；
2. **DOM chat-observation**（`readChatObservation` → `readFeedback`，`engine-actions.js:478`）：`confirmed_failure` 且非 recipient 时，扫描当前已核验 chat 层内叶子节点（`p,span,div`，无子节点、可见、不在消息气泡/输入区内），文本去空白、去尾部 `。！!` 后与 `REJECTION_RULES.texts` 全等 → `{code, reason, evidence:'matched-chat+platform-recipient-notice'}`；
3. `result.failureScope === 'recipient'` 或 readFeedback 命中 → `recipientRestriction = true` → `anomaly:false, skipped:true`（记 `confirmed_failure` 但不计入连续异常）；否则 `anomaly:true` 计入 `failedCount` 与连续异常。

`REJECTION_RULES` 精确文案（texts 数组逐字）：
- `DM_DUPLICATE_MESSAGE`：`重复发送 | 消息重复 | 请勿重复发送 | 请不要重复发送 | 请勿重复发送相同内容 | 消息已发送，请勿重复发送`；
- `DM_RECIPIENT_MUTUAL_ONLY`：`对方设置了仅和他互关的人可发消息，由于你不在范围内，暂无法给对方发送消息`；
- `DM_RECIPIENT_MESSAGE_LIMIT`：`给对方发送的消息已达上限，对方回复或互关后才能继续发送消息`。

### 3.4 私信历史状态机（`lib/dm-history-observer.js` + DOM）

**网络（protobuf 历史，被动）**：POST `https://imapi.douyin.com/v1/message/get_by_conversation`（cmd 301）或 `/v1/stranger/get_messages`（cmd 1002），binary 类型，请求体 ≤64KB、响应 ≤512KB。请求解析：信封 field1 ∈ `{301,1002}`、field2 序号；cmd301 体 field301：field1 会话串（participants 含目标）、field2=`1`、field3 shortId、field5 游标=`MAX_I64` 且无 field4/field7 → `fromLatestAvailable`；cmd1002 体 field1001：field1 shortId、field2 ∈ `[0,1]`。响应：信封 field1=命令、field2=请求序号、field3=`0`、field13=发送者（须 ≠ 目标，若提供 selfNumericUid 须一致）；消息条目 schema `{1:'s',2:'v',3:'v',4:'v',5:'v',6:'v',7:'v',8:'s',10:'v',12:'v',20:'v',50:'reject',51:'reject'}`：field2=`1`、field5=shortId、field7=发送者 uid、field6=`7` 且 field8 经 `plainText` 解出 → 我方文本计 `outgoingTextCount`；field10（毫秒时间戳，`946684800000 ≤ t ≤ now+300000`）→ `latestOutgoingAt`。

**state 枚举**（`dm-history-observer.js:75` 与 `dm-protocol.js:272`）：
- `already_sent`：任何一页解析出 ≥1 条我方文本（`outgoingTextCount > 0`）→ `reason:'本次网页历史响应存在当前账号向目标发送的文本记录'`，evidence `'im-protobuf-history:matched-request+conversation+sender;positive-server-id;outgoing-text-present'`；一旦为 already_sent，后续空页不可擦除（`result.state !== 'already_sent'` 保护）；
- `no_outbound`：`complete === true`（`fromLatestAvailable && hasMore(field3)===0 && !unclassifiedOutgoingCount && indexedMessages`）→ 完整可见历史无我方记录；evidence `'im-protobuf-history:cmd301;older-from-max-index;explicit-end;no-prior-outbound-in-available-history'`；
- `unknown`：其余（含页面关闭/abort 回退，除非已 already_sent）。
- 附加字段：`hasMore`、`cursorPresent`、`protocol/source: 'im-history-cmd301'|'im-history-cmd1002'`、`completeHistoryProven`、`observedMessages`。`no_outbound` 落库时要求 `complete===true`，否则 `saveContactObservation` 降级为 `unknown` 且不写库。

**DOM（chat-observation，`outreach-browser.js:368`）**：仅读当前已核验 chat 层（`[data-e2e="im-dialog"] [data-stack-layer="chat"]`，`activeChatLayer` 命中测试），且接收人证据（显式 uid 属性/链接或聊天头昵称与 profile 一致）成立；`messageMessageListlist` 恰一个；气泡需同时满足 `messageMessageBoxisFromMe + MessageBoxContentisFromMe + MessageItemTextisFromMe` 且 box/column/content/text 各恰一、嵌套完整、side/bottom 槽为空、无 `fail|error|sending|pending|retry|loading` 类名、无 `data-send-state`、`aria-busy!=='true'`，文本经 `.TextMessageTextpureText[data-apm-action="纯文本"]` 非空 → `history = {state:'already_sent', source:'browser_chat_dom', complete:false, lastSentAt:null, evidence:'matched-chat+outgoing-markers+empty-status-slots', outboundCount}`；否则 `unknown`（空聊天/失败气泡/未知结构一律不能证明「从未发过」）。

**资格联动 `workflow.dmHistoryEligibility`**：本业务跨账号历史（`contactKey = businessId|uid`）中任一 `pending_verification` → 禁止（「上次发送待核验，禁止自动重发」）；`noDm && noDmConfirmed` → 禁止；`alreadySent`（`dmCount>0 / dmState|dmOutcome === 'confirmed_success' / status ∈ ['dm_sent','followed_dm']` 或观察记录 already_sent）且 `repeat.enabled===false`（默认关闭）→ 禁止重复；发送时间未知 → 禁止；间隔不足 `repeat.intervalDays`（默认 7 天）→ 禁止；网站历史 `unknown` 走 `historyUnknown:'allow_initial'`（不阻止首次发送）。

**冻结**：发送前 `history.dispose()`（`engine-actions.js:448`），保证本次发送响应不会成为「历史证据」；`recordHistory` 以 JSON 指纹去重；`refreshHistory` 把观察快照同步给 `saveObservation`。

## 6. 潜在风险点 / 改进观察（仅观察，未改动代码）

1. **`仅自己可见`（send status=4）不携带 `failureScope:'recipient'`**：`parseSendResponse` 只对 status=3 挂 `failureScope`，status=4 走普通 `confirmed_failure` → `dmOne` 中 `recipientRestriction=false` → 记 `anomaly`，计入 `failedCount` 与连续异常（3 次即 `CONSECUTIVE_ERRORS` 整批暂停）；且 `REJECTION_RULES` 没有匹配「仅自己可见」类 DOM 文案，readFeedback 兜底同样无法降级为单用户拒绝。若平台用 status=4 表达接收人权限，会导致把单用户问题放大为账号级暂停。
2. **关注回执默认窗口仅 5 秒**：`createFollowReceiptObserver` 的 `timeoutMs` 默认 5000（上限 15000），`followOne` 未传 `deps.receiptTimeoutMs` 默认值。慢响应 → 落 `pending_verification` → 同账号再次关注被 `workflow.eligibility` 的 pending 检查阻断，只能人工核验。
3. **网站历史 unknown 不拦首次发送**（`historyUnknown:'allow_initial'`）：历史接口读不到（权限/删号/旧会话）时，即使此前私信过也可能再次发送；正向历史（already_sent）一旦取得则不可擦除，方向是安全的，但首发送前的「未知」风险需业务上知晓。
4. **legacy JSON 发送路径不核验**：`aweme/v1/web/im|message|private_message/.../send/` 只记录事件，不释放 `waitForReceipt`。平台若改用该协议，全部落 pending（禁止自动重发）——安全但可用性下降。
5. **`follow_status=4`（Requested）被判 unknown**：`profile-relation-observer` 只接受 `[0,1,2]`；「已请求关注未通过」状态会退回 DOM 控件判断（控件此时通常显示「已关注」/「关注中」→ 会被当成 already）。
6. **`readPageHealth` 依赖精确中文文案正则**：平台提示文案微调（如「操作过于频繁，请稍后重试」）可能导致 restricted/daily_limit 漏判，进而继续操作（未在代码中确认有兜底容错）。
7. **`visit` 健康重试上限 8 秒**：重试白名单仅 `PAGE_NOT_READY/LOGIN_PENDING/LOGIN_UNCONFIRMED`；超时后 `PAGE_NOT_READY` 抛出；且 `PAGE_NOT_READY` 不在 `stopClassError` 白名单 → 后续 `followOne/dmOne` 阶段的 `PAGE_NOT_READY` 按「单用户异常」继续处理下一位用户而非暂停任务（页面长期未就绪时可能对名单逐条失败直至连续异常阈值）。
8. **额度按「点击」计尝试**：`bumpAttempt` 在 click 返回 true 即计 `followAttempts/dmAttempts`，回执最终 pending 也占用额度（保守、防超发，方向合理，但需知晓「尝试」与「成功」双口径）。
9. **`prepareSend.click()` 成功后立即 `clearConversation(page)`**：会话会话期状态（editor/scope handle）随之销毁；后续 `readFeedback` 依赖重新读 DOM 与点击前捕获的 `profileIdentity`，若平台在发送后重绘聊天头（昵称/头像局部变化），限制文案可能读不到（`chat-observation` 要求接收人证据再次成立）。
10. **list→chat 行点击只执行一次**：`session.conversationSelected = true` 后 `TimeoutError` 仅返回 false 不重试点击，整体就绪窗口 2×`WAIT_MS`（16s）；慢机器上可能出现「有会话但从未点击」的 `DM_TARGET_CHAT_NOT_READY` 失败。
11. **`conversation-row` 在 im-dialog 内不校验行身份**（`outreach-browser.js:284`：`observedList` 分支 `evidence = {mismatch:false, hasTargetEvidence:false}`）：列表行点击仅靠「唯一候选行」+ 后续聊天头昵称比对兜底；若列表存在两条同名用户会话，`ambiguous` 阻断，属安全侧（未在代码中确认平台会渲染同名重复行）。
12. **好实践确认**：全程被动观察、从不重放请求；诊断只落白名单计数；发送前原子落 pending 防崩溃重发；`settledAttempt` 防覆盖人工核验结论；history 在发送前 dispose 防「新发送当旧历史」；protobuf 解码器为白名单 schema，未知字段跳过不解码。以上可作为后续迭代的基线。
